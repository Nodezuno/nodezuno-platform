# Single-host capacity and configuration

Status: current low-traffic AWS operating profile. One host and one web process with SQLite, not a highly available cluster.

## Runtime ownership

| Group | Operator responsibility | Scope |
| --- | --- | --- |
| Deployment identity | Exact `PUBLIC_ORIGIN`, `BETTER_AUTH_URL`, `NODEZUNO_DOMAIN`; direct versus trusted ingress | Web; origin supplied separately to the email worker |
| Core secrets | Independent `RATE_LIMIT_SECRET`, `BETTER_AUTH_SECRET`, `REVIEW_CAPABILITY_SECRET` | Web, with only the required subset sent to each worker |
| Payment evidence | Approved Mainnet mode, independent RPC configuration, confirmation threshold | Web and payment worker only; no wallet private key |
| Email delivery | `ZOHO_SMTP_HOST` and protected `ZOHO_SMTP_PASSWORD`; fixed `info@nodezuno.com` sender and operations inbox | Email worker and relevant web paths; not the payment worker |
| Topology | `single-host-sqlite`, one web replica, `systemd-single-host` worker owner, exact process role | Host-injected values in Compose; never user-selected form fields |
| Persistent data | `NODEZUNO_SQLITE_PATH` on the encrypted mounted volume | Web and separately leased workers on the same host |
| Deliverables | Region, private S3 bucket, dedicated KMS key, least-privilege instance role | Web delivery path; do not copy storage credentials into customer URLs |
| Launch decisions | Legal approval, payment enablement, public indexing | Explicit separate operator approvals; never inferred from a successful build |

The web, email, and payment environments are generated by the existing AWS deployment scripts. Do not replace their allowlists with a shared copy of every secret. Store secret values only in the documented private deployment environment and encrypted backup process, never this table or a release archive.

Run the existing redacted preflights in the correct configured process environment:

```sh
node scripts/preflight-deployment-topology.mjs web
node scripts/preflight-review-application.mjs
node scripts/preflight-stablecoin-payments.mjs
```

Payment preflight performs read-only Mainnet RPC requests. It does not sign or send a transaction. A passing configuration check does not establish actual customer email delivery, successful recovery, legal approval, or external TLS/alert health.

## Worker budget

The email worker claims at most 25 rows, reserves 18 seconds to finish a row within a 45-second scheduling budget, and stops claiming when that reserve is reached. This avoids a sequence of 25 slow provider calls occupying the shared background lock for more than 200 seconds. Database or OS stalls can still exceed a scheduling budget, so the existing 180-second systemd deadline remains a final safeguard.

Unclaimed messages keep their attempts and remain available to the next timer. An in-flight row finishes through the existing lease, idempotency, acceptance, and retry rules. Aggregate `outbox_pass_completed` logs now include `timestamp`, `service`, `durationMs`, and `budgetExhausted`, without message content or recipients. A budget-limited pass is not itself an error; growing backlog, stale heartbeats, or repeated service timeouts require action.

Both workers still share the one-host nonblocking lock. Do not treat lock contention as permission to run a second web replica. Systemd exit code 75 and repeated heartbeat gaps need investigation. Dedicated lock-skip metrics and database write-latency instrumentation remain follow-up work.

## Capacity decision record

Use a private record containing only aggregate values:

- observation window and release digest;
- peak request and worker load;
- database and WAL sizes, disk and inode utilization;
- measured write latency, busy-error counts, and customer impact;
- oldest pending payment/notification age and pass durations;
- last verified backup and restore date, measured recovery time and data loss;
- required recovery and availability targets;
- decision, owner, date, and next review trigger.

The host collector publishes database size, WAL size, and data-volume inode utilization alongside the existing readiness, payment, notification, disk, and backup metrics. Missing collection is not reported as zero database size. These are additional CloudWatch custom metrics when this host bundle is deployed; include them in the AWS monitoring budget. Busy-error and write-latency measurements are not yet collected by that script and must not be claimed as deployed telemetry.

Use the existing business triggers in [AWS_COST_MODEL.md](../AWS_COST_MODEL.md#move-to-postgresql-and-ecs): customer-affecting SQLite contention, another web writer, required recovery below the current profile, availability commitments, or repeated single-host incidents. Follow the [architecture prerequisites](../AWS_ARCHITECTURE.md) before migration. Adding replicas to a local SQLite volume is not a scaling strategy.
